# Navigation and locating changes

This entry defines the method. Mutable paths, responsibility mappings, state and gaps belong only in [PROJECT_NAVIGATION.md](../../../PROJECT_NAVIGATION.md). Navigation is development guidance, not a runtime router, user database or authorization system.

## Required input

Use the current task, read/write boundaries, workspace and problem. If a needed module is unavailable, record what cannot be verified and continue independent work. Do not scan unrelated projects or create a replacement module.

## Locate the change

1. Start at [AGENTS.md](../../../AGENTS.md) and the relevant change entry in navigation. Separate explicit requests, confirmed decisions, implementation facts, proposals and unsupported inferences.
2. Find the conceptual responsibility and authoritative data owner. Follow only the needed path: **UI → Bridge/IPC → judgment or tool → integration/storage → relevant existing checks**. Several responsibilities in one file do not require several services.
3. Verify the index against files and callers. An existing path, inspected implementation, test source, historical report and current runtime observation are different evidence. Names and check titles do not establish a completed feature.
4. Record both **A: implementation/integration extent** and **B: operational state/evidence date**. A runnable independent component is not necessarily integrated; a weather tool does not establish current permission or a successful network response.
5. For user-related changes, consult the [object boundaries](../../../PROJECT_NAVIGATION.md#find-the-real-owner). Say what must be read and what must remain unread. Accounts, credentials, permissions and user isolation are cross-cutting boundaries rather than model profile fields.
6. Identify the smallest coherent change, affected owners and derived results, and suitable verification. Without implementation authorization, stop at location and contracts. Account connections and external writes require their own authorization.

## Maintain the index

Update the corresponding navigation entry, state and evidence date when adding, deleting, moving or changing the responsibility of an owned file. Verify an unindexed file before adding it; do not exclude it simply to make a check pass. Dependencies, build outputs and binaries can be grouped by declared directories. Private runtime databases do not belong in a public index.

Keep one path authority. Other skills, README and design records link to navigation instead of maintaining competing trees. Old paths, dimensions and screenshots are evidence for their particular version, not overrides of current facts.

## Completion

Hand back the correct entry points and call relationships, owners, A/B state, fact/plan distinction, minimum missing information, suitable verification and work not performed. Inspect local Markdown paths, anchors and entries against the current tree, and commands against the real `package.json`. Do not invent a documentation checker or add a test runner for document synchronization. A document review does not run the app or query accounts and cannot prove domain behavior.

Consult [project foundations](../project-foundations/SKILL.md) for major mission decisions and [product design](../product-design/SKILL.md) for experience design or review. Routing is not a reason to load every document or create empty map, weather or user skills.
