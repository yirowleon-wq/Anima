# Position inputs and workout continuity

Develop map, route and workout behavior using manually chosen origins, explicitly imported records, or app-internal virtual positions and trajectories. Each path depends on its actual implementation; this document does not establish that every input workflow already exists. Keep the source and its limits visible: a simulated point is not a device observation, real arrival, a completed physical workout or official activity credit. Do not acquire real device location or enable OS location services or request or grant location permission on any platform, browser, emulator or guest.

The workout owner, map matcher and retained record types contain important parts of this contract. The in-process [simulated source](../../src/main/simulated-location.ts) defines a map position at the center of validated active-map bounds and a deterministic moving workout track. The workout choice uses `source: 'simulated'` and the identity `anima-simulated-track`; its points use `source: 'anima-simulated'`, `transport: 'simulated'`, `provenance: 'simulated'` and `mock: true`. It does not need a device or generate cadence. The ordinary user workflow and recovery need their own actual verification; source code and this document do not establish those outcomes. An imported or manually supplied point retains its own source rather than being relabeled as that generator.

## Keep the original input and its meaning

The existing [workout input types](../../src/shared/workout.ts) distinguish the original coordinate and declared reference, source timestamp, host receipt time, accuracy and its confidence, altitude and its datum, speed, heading, source identity, provenance and mock status. Optional values remain unknown when absent; a convenient default is not an observation. The current coordinate contract is EPSG:4326 longitude/latitude. Other formats require an explicit, evidenced conversion before entering that contract.

Keep raw coordinates and timestamps separate from filtered coordinates, map-match candidates and calculated distance. A source identity, a run or subscription identity, and the authoritative workout ID each answer a different question. A manual route origin supplies a place from which to calculate a route, not a stream of movement. Matching a point to a road or venue is a candidate result with its own map version and uncertainty; it cannot establish physical passage, arrival or access. See the [map matcher](../../src/main/map-workout.ts) and [map quality directions](../scenarios/MAP_QUALITY.md).

For a sequence, retain each accepted or rejected input and its actual quality reason. Unknown accuracy, stale or invalid time, an outlier, an unselected source and a source change have different consequences. A source change starts a new segment rather than inventing the path between sources. A simulated or unknown observation cannot later be promoted into a physical-device record merely because a later point appears more certain. Do not infer cadence from map motion, speed or assumed step length; without an appropriate input it remains unknown.

## Time, freshness and bounded delivery

Preserve the source time and receipt time separately, even when both are supplied by the same host. A monotonic interval is comparable only within its declared clock identity. Never correct an unknown offset by silently rewriting the source timestamp. Expired, out-of-order, future-dated or weak input must remain distinguishable from an unavailable source. The existing `workoutFixTime` rule uses a 30-second default age bound and five-second future tolerance; the [workout owner](../../src/main/runtime/workout-session.ts) also separates segments across gaps over 15 seconds. These are current code values, not evidence that a particular virtual run has been exercised or that another protocol has the same clock.

Some retained records include command/reply clock correlation. Preserve the original command and subscription IDs, source process and observed time, host send and receipt times, host monotonic duration and any acknowledged-anchor age. Their time result is an interval, not an invented exact midpoint. The retained validator limits the exchange and, where the basis is command processing, the acknowledged-anchor age to ten seconds; it rejects wall-clock/monotonic disagreement over 250 milliseconds. Older records without an exact processing-time basis must not gain precision retroactively. These fields are for interpreting compatible retained inputs, not a reason to start a platform location service.

When an asynchronous producer needs buffering or a lease, use a bounded queue and bind every message and renewal to the original run and workout. Expiry prevents further production; it does not by itself prove that the receiver observed a stop. Earlier transports used buffers of 64 and 16 positions, with renewal every five seconds and expiry after twenty; those were adapter-specific values, not requirements for an in-process generator. Preserve the boundedness and truthful state transition without inventing a remote protocol where none is needed.

## Stop, cancellation and restoration

One workout owns one active input stream. An explicitly identified run or subscription cannot be taken over by another workout. A duplicate start for the same live identity must not create a second producer. A rejected or late command, callback or older generation cannot revive a stopped or cancelled run. Stop must actually release the producer and its pending callbacks; a successful local return may confirm a local producer has stopped, while an unacknowledged asynchronous stop remains unknown.

Pause, finish, revocation and cancellation each stop the affected input without implying the others. A resumed session needs an explicit continuation and a new segment. Restoration reads the retained record; it does not silently restart the input or add downtime to active time. A retained legacy record with an unconfirmed stop must remain unconfirmed: selecting a different source or stopping a new virtual source does not acknowledge the original attempt. Preserve enough original identity to explain and recover that state without contacting a device.

Cancellation fences the specific workout and its dependent source before old asynchronous results can restore it. Local deletion, source retraction and producer stop are separate outcomes: progress and failures remain retryable against the same identity, and a failure in one does not justify claiming all succeeded. The [workout owner](../../src/main/runtime/workout-session.ts) and [private draft storage](../../src/main/runtime/workout-storage.ts) retain session-only and encrypted-local choices, revision checks and recovery metadata. The raw track stays with that owner; any model-facing projection follows its own permitted source scope.

## Evidence for a working path

For a changed source, inspect the actual ordinary entry, input provenance, current map frame, quality and freshness, and resulting owner state. Exercise the affected pause, cancellation and restoration paths with virtual or explicitly imported inputs, including any genuine unknown stop, and inspect the resulting records. Do not claim an implementation, working recovery or a mobile-host result solely from these requirements, a type declaration or a platform label. The [capability record](../CURRENT_STATUS.md) and [development roadmap](../DEVELOPMENT_ROADMAP.md) retain the separate observed and future-work boundaries.
