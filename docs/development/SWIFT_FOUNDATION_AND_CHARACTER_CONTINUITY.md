# Swift foundation and character continuity

This is a future commission for Quinn, not a record of implemented or accepted work. It precedes the twelve existing stages and strengthens their **38 existing work blocks**. The individual [work orders](WORK_SEQUENCE.md), stage exits and [memory/context gates](../scenarios/MEMORY_GATE_SEQUENCE.md) remain in force; this document does not replace or renumber them.

The maintainer has confirmed the order: first develop the native macOS desktop application on Quinn's Mac, then extend the product to independent iPhone and iPad hosts in Stage 11. React itself does not prevent an application from running on a Mac: this is the chosen native-product direction, not a technical consequence of using React.

## Stage 00 — Make the existing product a native Swift foundation

The current product is Electron, React and TypeScript, with a pinned Python Hermes sidecar. Its Windows observations do not establish Mac operation. Begin by recording the actual Mac architecture, Xcode/Swift toolchain, available SDKs, signing and runtime conditions, current repository version, data owners and a capability-by-capability inventory. Use the existing application and original work as the baseline. Do not copy credentials, private profiles or databases into a development report.

The goal is to rebuild the existing desktop experience as a real Swift/SwiftUI macOS application, carrying its useful behavior and data forward. This is a migration of the product, not merely a Swift wrapper around an unchanged React page. Preserve conversation, the same composer and drafts, source selection, notes and materials/PDF, calendar and action recovery, maps and workouts with permitted virtual inputs, interactive creations, all ten editable character identities, four themes, and existing settings, accessibility and return paths. The inventory must map each existing capability, state and persisted format to its new owner, migration and ordinary-use evidence; do not silently omit difficult features. Keep retained art and the current experience usable while corresponding native pieces are built.

Start with an integrated vertical slice and then migrate the remaining existing surfaces in bounded pieces. Stage 00 exits only when the current product's required existing capabilities have usable native destinations and the relevant data and recovery are reconciled; the first slice alone is not the completed rewrite. Stages 01–12 still own their larger redesign, unfinished full-cast performances, new capabilities and full exits. Do not make the entirety of those future improvements a prerequisite for starting the native foundation.

### One runtime and explicit ownership

Trace and retain the existing `src/main/harness.ts → src/main/runtime/hermes.ts → runtime/hermes/sidecar.py → pinned AIAgent` path before choosing a host design. SwiftUI is a UI and host direction; it does not establish that Node, Python, Hermes, all native libraries or the model provider can be embedded in Swift. On the actual Mac, establish a supported packaged integration and process lifecycle for that single loop. A bridge must have a finite, authenticated surface; the existing React renderer keeps its finite preload bridge while it remains in use. Do not add a second permanent assistant brain, fact store, action dispatcher or independent writer for the same object. Product implementation remains under `src/`; any host adaptation must respect the existing project boundary and preserve an independently runnable application.

The main host retains ownership of credentials, SQLite, permissions, network, tools and effects; the native interface accesses those responsibilities through the finite bridge. Map each old record and revision to one authoritative owner; preserve source references, user-created roles, historical speakers, saved work and draft identity. Make cutover, concurrency, transactional migration, cancellation, rollback and reopening explicit. A rollback cannot restore forgotten material, expired approval or repeat an unknown external action. Existing working paths remain available until their replacement is verified; do not require Windows to disappear merely because the Mac is being migrated.

### Harden the harness, memory and character from the beginning

Before broader redesign, repair observed problems in current turn assembly, streaming, tool and source boundaries, cancellation, model failure and recovery. Make the permitted current request, selected object, source revision and selected character available to the same primary model before it decides how to investigate. Keep local-only material local before any cloud classification. Model/tool progress must correspond to an actual finding or state; stop stale output when a target, source or permission changes. An unknown action result requires inspection of that original attempt before retry. Simplify only where equivalent capabilities, provenance and recovery remain intact.

Improve memory where it affects actual help now: use original permitted words and the current correction; distinguish a stable preference from an exception, a user statement from an inference, and a saved character configuration from personal history. Retain original ownership and lineage for revision, source withdrawal and forgetting; recheck scope before reading, transmitting, adopting or retaining. Handle unavailable sources and late results honestly. Stage 03 still completes the six-layer redesign and its broader acceptance; an early improvement does not claim that exit.

Read the complete [passport](../characters/README.md) for the selected character, their actual saved configuration and the current exchange. Their personality participates in attention, interpretation, tool choice, response, disagreement, waiting and recovery, rather than being pasted onto a completed generic answer. An explicitly user-created character uses its own saved identity. Preserve character, appearance, history and old message authorship as distinct things; switching appearance or model must not rewrite the person or past speakers. Luna is the current live **model connection** in this baseline; the selected companion is the speaker. Do not equate a model provider with the selected character or call the character an output, input, test subject or acceptance result.

Audit all user-visible conversation, progress, notices, failures, permission explanations and return states for engineering language and objectifying presentation. For example, labels such as “Luna returned”, “input accepted” or “test passed” must not appear as the companion's ordinary speech. Necessary engineering terms, exact failure details and check results remain available in appropriate diagnostic or development contexts; do not conceal a real limitation or make a failed operation sound successful. A genuine host notice may use clear neutral language when no character response exists; never invent a character utterance, feeling, tool result or progress event. Where the character does speak, use the selected persona and the facts of that moment, with room for silence and disagreement. Illustrative alternatives are not a canned dialogue script, keyword filter, persona classifier or second answer-restyling engine.

### Ordinary-use evidence and exit

On the actual authorized Mac, establish ordinary installation, launch, supported packaging and process restart. Use the real model route and selected persona to discuss a permitted source, correct the target or remembered understanding, wait for a real tool result, handle an unavailable source or model, keep an editable draft, leave and reopen the same work. Observe the actual character's participation and the accuracy of each visible status. Exercise the other existing feature families and their relevant save, cancel, error and return states against the inventory, including a genuine persisted item and an original action attempt where appropriate. Inspect the integrated native views, character interaction and motion at relevant window sizes, keyboard access and reduced motion. Use the project's applicable existing checks; do not author new tests or runners unless separately requested. Fix a correctable defect and repeat its original trigger.

Record the actual Mac, architecture, build, product-model identity, migrated capability/data correspondence, observations and any unmet condition in the existing status and continuation records. A build, a single character sample or a simulator does not establish full parity. Missing Mac access, signing or a dependency remains a concrete unfinished condition, not a reason to claim an Electron build is native Swift.

### Implementation responsibilities

Organize this substantial prerequisite with a lead and eight substantive implementation subagents. The lead first understands the whole baseline, assigns exclusive file ownership and one writer for each shared contract, integrates their work and personally accepts the result. These are implementation responsibilities, not eight reports; the actual file boundaries are chosen from the then-current code.

1. Establish the native macOS host, toolchain, packaging, process lifecycle and finite bridge to the existing loop.
2. Migrate the existing conversation, composer, materials and note surfaces to native controls while preserving draft, focus and source continuity.
3. Harden the primary turn path, real streaming and tool progress, cancellation and failure recovery without adding another assistant engine.
4. Improve source-backed context, current correction, memory retrieval, lineage and withdrawal barriers under existing permissions.
5. Make each selected character's saved identity and passport effective during interpretation, tool use and visible response; audit mechanical user-facing language.
6. Carry current calendar, action, map, workout and interactive-creation capabilities through their real authoritative owners, including safe recovery.
7. Migrate the remaining native appearance, accessibility and interaction relationships using the existing design and art requirements, with four themes and retained assets.
8. Reconcile data and capability correspondence, perform integrated ordinary-use inspection, repair cross-boundary failures and record actual platform evidence.

These responsibilities do not start implementation merely by appearing in this plan.
