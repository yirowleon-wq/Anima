# Future map implementation and integration commission

**This plan describes map implementation and integration work; it does not start that work by itself.** Read the [current-authority note](../README.md#current-authority-and-future-work). Current user instructions, the location prohibition and restrictions on new test engineering prevail over historical tooling proposals.

Own implementation and integration for the explicitly frozen map scope. The goal is traceable facts, legal spatial relationships and consistent restrained dark warm gray/gold expression, capable of meaningful acceptance. Preserve the existing stack and successful interaction. If a local mechanism needs replacement, first prove how it causes the defect; do not use the task to rewrite the whole product.

## Understand the real project before choosing an implementation

Locate this package, read the full [research report](../research/REPORT.md), [method](../policy/ENGINEERING_METHOD.md), [rules](../policy/CHECK_RULES.md) and [schema guide](../templates/SCHEMA_GUIDE.md), then undertake the [baseline](BASELINE.md). Older instructions provide problem context; their weaker “substantially less rough” criterion cannot replace explicit gates. Templates are not actual data. The historical package's six independent-chat arrangement is preserved as responsibility design, not a current command to open chats or prohibit the team's authorized subagents.

Before baseline is established, do not alter production coordinates, contours, heights, styles, layer visibility or routing. Read, purposefully experience the current version, export nondestructive data or use minimal read-only audit instrumentation only within actual authorization. Do not turn understanding into a building-by-building recording exercise. Record real checkout/worktree, commit, uncommitted changes, startup entry, stack, data directories, generators, render chain and existing sources. Preserve user work and unknown assets.

## Establish a traceable fact layer

Separate factual geometry, semantics, 2.5D/3D representation, cartographic expression and navigation/interaction. Important objects have stable `feature_id` and explicit mappings among source, canonical entity, generated instance, label, entrance and route object. Names, contours, road relations, physical width, height and base height have distinct claims; one high-confidence object label cannot stand for all fields.

Resolve datum, axes, units, provider conversion, projection, registration, render origin and vertical reference for each input. Save registration control points, fitting/independent sets, residuals and applicability extent. Until key references are verified, do not patch by moving a building a little or widening a road by eye. Use the shared transformation chain; hidden per-object offsets are unacceptable.

Establish each source's allowed use before acquiring/using it. Public viewing, manual reference and withholding the original do not automatically permit extraction, derivation or redistribution. Do not sweep public tile services for whole-area review. Never upload accounts, keys, private imagery, restricted tiles or unlicensed vectors. Find lawful alternate evidence when a source is restricted.

## Organize repair by failure mechanism

Build the complete entity denominator, generation rules, external missing candidates, AOI partitions, classes and accountable issue records. Use existing applicable full-set operations; individually review critical roads, bridges, entrances, complex buildings, sports facilities, anomalies and reported regions. Repeated micro-objects use complete generator membership, rule review and real member samples, expanding to the class when a systematic fault appears. Visible objects or a few screenshot areas are not the whole scope.

For each defect record rule/class, `feature_id`, location, candidate cause, evidence gap and affected class/neighborhood before choosing a shared repair. Follow source → canonical → derived → rendered layers. Check graph connectivity, physical width and screen casing separately. Decide bridge/tunnel/passage/overhang relations before treating a 2D intersection as illegal. Neither deleting every crossing nor inventing a layer/bridge flag is acceptable.

Keep building complexity within evidence. A trustworthy simple volume needs checked contour and reviewable height basis. Do not duplicate full parent and parts. Wings, links, platforms and roofs each need evidence. Unknown heights remain unknown; random defaults, universal flattening or hidden buildings cannot pass. Sports facilities share rules but retain independently supported parameters; do not force two different facilities to be identical or leave unexplained missing markings.

Preserve dark warm neutral/gold, restrained transparency and the intended technical clarity. Map features, surfaces, walls, shadows and interaction highlights use semantic tokens. Consistent lighting variation is valid; arbitrary per-object exceptions are not. Identify uncertain land surfaces before changing them. Inspect labels after actual projection with priority, scale bands, occlusion and occupied UI space. Do not hide all labels to eliminate collisions. Current four-theme and no-green-interface rules remain authoritative.

## Checks and states must mean something

Use Q01–Q28 as a failure-mode catalog, bound to the real stack and existing reliable operations. A result identifies object/location, input version, applicable members, actual measurement or observation, criterion, legitimate exception, output locator and next repair. A checker must actually detect its stated failure and discriminate legitimate cases. Where new test authoring is not authorized, use direct existing evidence rather than creating a fixture/runner in disguise. Missing sources, errors, timeouts or unexamined scope cannot be PASS. Freeze calibrated, unit-bearing thresholds before modification; do not loosen them to improve a color on a dashboard.

Derive object state from evidence and results. Missing applicable checks, stale dependencies, empty references, critical conflict or unknown neighborhood prevents readiness. Upstream changes invalidate dependent results. Hiding, reclassification, deletion or LOD reduction cannot shrink the completion denominator without an accountable decision and mapping. Report actual defect closures and blockers, not run counts, screenshot totals, video duration, test lines or document pages.

Human review uses normal finished rendering, a focused ID/semantic view and source/difference views with a clear question. Static inspection locates geometry faults; ordinary continuous interaction checks camera, label/LOD transitions and route linkage. Recheck the affected set and neighbors after a batch. A shared reference/generator/topology/integration change triggers its actual broader dependencies, not an indiscriminate recording after every object.

## Real ownership and one integrated version

After baseline, instantiate contracts from actual exclusive files rather than mechanically creating six writers. Stabilize sources/reference first; roads, buildings and grounds can then own independent writes. Styling can study read-only before approved interface/write boundaries. Independent review does not silently modify production data. Every writing assignment binds actual session/worktree where applicable, baseline, schema, alignment, object membership, precise allowlist and forbidden range. One file has one writer. A monolithic file may require parallel research and serial integration.

Use only real current client/team capabilities. Do not report nonexistent independent sessions or replace a healthy session because a wait/tool call/compaction was inconvenient. Each family submits scoped `MERGE_READY`, research readiness or a blocker, never whole-map acceptance. The integrator checks duplicate repairs, coverage conflicts, lost objects, stale references and unresolved handoffs before producing one integrated version. Old branch images and results do not automatically pass that version.

## Phases, gates and exit

The [twelve map work phases](phases/README.md) preserve dependency gates, distinct from the product roadmap's twelve stages. Incremental geometry review begins with the first real change; phase nine is complete audit, not the first check. Interleave independent work only with explicit satisfied dependencies. Progress autonomously through already-authorized prerequisites; preserve a real blocker when key access, evidence or authorization is missing while continuing independent work.

Submit a release candidate only when scope reconciles; zone/class/object review is genuine; key source/registration chains are suitable; applicable results are fresh; P0/P1 are zero; critical and high-risk human review is complete; no required region is unchecked; no unsupported massing, illegal penetration or confirmed unexplained break remains; residuals and rights are disclosed; all changes are integrated; and actual finished-view/interaction inspection is reviewable. A limited P2 delivery needs actual designated acceptance, not the integrator's unilateral severity reduction.

Deliver the real implementation/integration commit, reproducible running instructions, structured records with only useful derived views, actual rule outputs, a small purposeful set of lawful source/difference views, remaining scope/issues and the filled [acceptance card](FINAL_ACCEPTANCE.md). Exclude restricted media, caches, secrets and unrelated artifacts. Preserve genuinely useful existing verification assets; the word “test” alone is not a reason to delete them.

Report `IN_PROGRESS`, `BLOCKED` or `RELEASE_CANDIDATE`; actual final acceptance belongs to the designated acceptor. A goal stop signal is not map acceptance. A recoverable checkpoint identifies current commit, next eligible phase, remaining members, blockers and next concrete action. A phase ending or a budget/tool limit cannot become whole-map completion.
