# Substantial development stages

These stage plans describe Anima's future development. The current implementation, working materials and retained art provide starting points; they do not by themselves complete any of the twelve formal stages.

Read the current capability record and continuation before selecting work and establish the actual tool, platform and authority conditions. The plans follow [the full roadmap](../DEVELOPMENT_ROADMAP.md), whose dependencies, eight substantive responsibilities and completion gates remain authoritative.

The [Stage 00 Swift foundation](../development/SWIFT_FOUNDATION_AND_CHARACTER_CONTINUITY.md) precedes these twelve stages. It strengthens the existing 38 blocks without renumbering them and does not establish a completed native application by itself.

Choose a coherent substantial unit from the current stage, with a usable outcome and clear next entry. A stage may span healthy sessions. No single-character sample, static fallback, fixed demo, pass count or document completes its wider stage.

For the **38 individual work blocks**, use the [work sequence](../development/WORK_SEQUENCE.md) and its three work-order files. Each block connects the stage plan to ordered readings and artwork, dependencies, a substantial outcome, observable finish and a specific stop/resume point. The roadmap remains the source of stage goals and exits.

Every stage and block now carries its critical frontend/backend, GPT Image, first-chain/cast expansion, acceptance and pause/resume wording directly in the body. The [200 memory/context requirements](../scenarios/MEMORY_GATES.md) also have actual item-specific acceptance text in their assigned blocks and a [complete 38-block map](../scenarios/MEMORY_GATE_SEQUENCE.md). Source and expected outcomes are design material for engineering; the acting product model receives only current input and permitted originals.

The [instruction audit](../development/INSTRUCTION_AUDIT.md) records direct coverage and reference checks. It describes documentation acceptance, separately from future product, motion, model and native-device evidence.

Each plan begins with the experience to create and retains the technical responsibilities needed to make it real. The roadmap, [technical boundaries](../development/TECHNICAL_BOUNDARIES.md) and [tooling](../development/TOOLING.md) provide complementary implementation detail.

Use existing checks and normal product entry points. Do not add tests, fixtures, assertion cases or scripted runners without an explicit request for test development. Actual UI, motion, sound, state, model participation, sources, native platforms and external conditions require their appropriate evidence. Correct in-scope defects before accepting a unit. Record unmet conditions truthfully without reducing or silently dropping their goals.
