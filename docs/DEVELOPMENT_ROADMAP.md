# Anima development roadmap

Anima should be a place worth returning to: a companion can take a difficult proof seriously, make something unexpected, disagree, enjoy a joke, or share an afternoon with no outcome to report. The same conversation, source passage, draft, route and unfinished thought should survive a change of mind, a page change and a return. Character begins in attention and judgment, including what to investigate and how to help.

This document defines twelve long-term engineering stages and their 38 substantial work blocks. A [Stage 00 native Swift foundation](development/SWIFT_FOUNDATION_AND_CHARACTER_CONTINUITY.md) now precedes them; it is a prerequisite, not a renumbering or a claim that an existing block has been completed. It also carries the first Harness, memory and character improvements through the 38 blocks. [CURRENT_STATUS](CURRENT_STATUS.md) owns the actual implementation and observation baseline. The current desktop review build, the first character sequence, a successful model request and a complete stage are separate milestones. Reading this roadmap does not start implementation.

## Current experience track

The main track uses an intentionally fictional campus with actual authored, routable topology and user-chosen fictional or sample material. These are complete product settings, not placeholders awaiting a real school. Their local operations, Luna model participation, visual quality, source identity, revisions, actions, saving and recovery must genuinely work. Real-campus mapping, virtual student-profile construction, private accounts and API connections are not prerequisites. Fictional records stay explicitly fictional; local success never becomes official enrollment, attendance, travel or provider acceptance. Luna is the current sole live product-model route.

Across desktop, browser, iOS, Android, emulators and guests, never acquire actual device location or enable OS location services or permissions. Develop and exercise the complete map, routing, camera and workout workflows with clearly labelled app-internal simulated movement, manually chosen origins and explicit non-personal map or sample imports. Preserve source, time, quality, gaps, cancellation and recovery. Simulated coordinates and arrivals do not establish physical presence, travel or arrival; real location acquisition is not a completion goal.

Preserve optional provider seams, import support and the complete external-integration goals as separately chosen future extensions. Block 02-C is such an optional extension: the main path is 02-A/B → 03-A, and an unselected provider does not hold Stage 02 or 12 open. Entry and exit gates apply to the selected track. This does not waive a promised independent native host, full motion or another selected outcome: each still requires its actual platform, model and experience evidence. If a real external action is separately selected, its original authority, unknown-result inspection and same-attempt receipt remain mandatory for that claim.

## How a stage is developed and completed

Each formal development stage requires one lead and **eight substantive implementation agents**. Ordinary review or documentation work does not automatically start a stage. The lead first reads the stage plan, the relevant complete materials, the integrated product and the stage’s goals. They then assign exclusive file boundaries, including exactly one writer for every shared type, schema, bridge, common style and asset manifest. The eight responsibilities below are real implementation responsibilities, not eight reports. Adapt file assignments to the current code; a proposed filename is not evidence that the component already exists.

The team must carry **at least 85% of the substantive implementation, integration, algorithm/source adaptation and module-verification work**. Each agent owns a coherent module, its error and recovery paths, and its integration. The lead owns the final product judgment, inspects the combined result and repairs or returns every observed in-scope gap. This obligation does not justify changing healthy code to reach a line count, splitting a small edit into artificial work, or requiring three revisions when there is no defect. Substantial work and observed outcomes determine acceptance.

Develop one meaningful usable block at a time. A block can span healthy sessions; it has an experience goal, dependencies, a current object/version, an observable end and a next entry. Start from the experience and why it matters, preserve important behavior, and leave room for design and engineering judgment. The [first stage plan](stages/01-shared-attention.md) is a starting point.

Use the selected model and effort. Keep healthy sessions through tool errors, waiting and normal compaction. Before stopping, save the current work and a concise continuation: version, usable result, actual observations, remaining condition, current object/draft and one concrete next action. Do not promise that every block fits a fixed allowance window. A saved Markdown plan does not execute itself.

Every stage retains these completion conditions:

- Its original workstreams, shared experience requirements and explicit exit conditions apply to the selected track. Optional unselected external integrations remain preserved design material, not prerequisites or unmet core gates. A first sample still does not close promised characters, pages, actions or independent devices.
- Exercise ordinary product entry points and the relevant existing `check`, `test`, `test:hermes` and `build` commands. Static inspection, mechanisms, real model use, current interaction, assets and devices provide different evidence. Do not author or expand test cases, fixtures, suites, harnesses or runners without an explicit request for test development. Direct existing API calls and scoped visual capture/comparison remain available.
- Inspect the actual integrated rendering, long English, mathematics, wide/narrow layouts and affected interactions. Observe motion at normal speed, interruption, keyboard, mute and reduced motion; a screenshot cannot establish those processes.
- Fix each observed in-scope defect and repeat its original trigger. Record an actual external dependency as incomplete, with its attempted alternatives and smallest missing condition. Documenting a blocker does not make the blocked behavior pass.
- Keep location services and permissions off on every host, app, browser, emulator and guest. Use simulated feeds, manual origins, configured public references or explicit non-personal sample imports; never acquire real device position. Preserve the map and activity interfaces for those inputs and exercise their real UI, state, errors and recovery. Other platform/device evidence is still required for the outcomes claimed.
- Selected external effects, account integrations and publication require their actual authority and evidence. A source push is not an application release.

### OpenUI and interaction: stages 04–09 establish the complete replacement

Design the entire cycle: authoring context and compact primitive signatures → finite validated composition → closed streaming units → render and bounded layout feedback → direct user manipulation → real ProgramLocalState/CAS → send-time snapshot → model reading and incremental change → save, return and reopen. Preserve compatible existing DSL/AST and primitives where sound; a new language is optional. The replacement covers authorship, validation, execution, layout, inputs, source bindings, modification and recovery rather than a collection of new cards.

One composer continues through conversation, reading, study, notes, maps and scheduling. A view, a program, a source selection, local input, business action and receipt have separate identities. The user can take over, accept one change, reject another, cancel or return without losing the draft or focus. Exact text/figure anchors, geometry, units, assumptions, audio and conditional explanation share the same real parameter relationships. A late program patch cannot restore initial values over a newer user edit.

Interaction work begins in stages 04–05, becomes physically coherent across stages 06–08, and reaches the complete general composition system in 09. Stage 10 supplies demanding sensory and everyday-life proofs; stage 11 supplies independent device hosts. Preserve the current working generation and input-return path while replacing it. A fixed topic template, an image of a page or an isolated sine demonstration cannot stand in for the full system.
