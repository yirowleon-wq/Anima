# Mobile continuity requirements

This is a catalog of **72 preserved design specifications**, each currently **not exercised by this document**. It creates no executable cases, fixtures, suites or runners and grants no device, account, model or action permission. D/A/V/H/P/R/X identifiers belong to this mobile catalog, independently of the twelve-stage roadmap. Existing implementation, a successful mechanism check, a simulator observation and a real-device result remain different evidence.

The product direction is an independent iOS/Swift and iPad host first, followed by Android at comparable quality. Existing React surfaces, maps, artwork and interaction contracts remain assets to preserve; reuse or native translation requires an explicit equivalence decision, not a generic replacement chat interface. An embedded web surface is an option to investigate, not a reason to assume Node, Python or Electron runs unchanged on a phone.

The phone must own its private data, credentials, permitted network calls, action state and recovery. A computer may aid development without becoming a required gateway. Distinguish the ordinary distributable app, a separately authorized personal enhanced experiment, and a vendor-qualified integration. A permission dialog, debug identity and vendor entitlement are different conditions. Platform-specific requirements stay conditional rather than being marked passed on another platform.

For future work, record actual outcomes as completed, failed, externally blocked, not exercised or genuinely inapplicable with a reason. Blocked required scope remains incomplete. Prefer actual owner state, receipts and OS observations, with direct human inspection of language and interaction. Never substitute a model's assessment, screenshot count or a template status for the outcome. Use existing checks and normal entry points; new test development requires explicit authorization. All observations need the real version/build, device/OS, inputs, outcome and evidence location, with secrets and private content excluded from shareable records.

D01–D08 and V01–V12 retain release-quality significance. A01–A10, H01–H10, P01–P12 and R01–R10 retain critical behavioral significance within their actual platform scope. X01–X10 are critical only within a separately authorized enhanced experiment; ordinary distribution must exclude their elevated implementation. Missing a device or permission is not a pass, and success in one track cannot certify another. Use an isolated synthetic workspace for any authorized enactment, without real account or production side effects, and record actual preconditions.

**OS location services and location permissions must remain off on every platform, including emulators and guests.** Position-related specifications use manual origins, explicit imports or app-internal virtual positions and trajectories. Preserve source/provenance, quality, expiry, unknown states, cancellation and recovery. A simulated trajectory is neither real arrival nor official activity credit. These requirements do not claim that an app-internal virtual workout source is already implemented. Read the [dated research references](MOBILE_REFERENCES.md) before relying on a platform claim, and verify current official documentation at implementation time.

## D · Development workflow — 8 specifications

### D01 · One-source visual development surface

Situation: open the repository's ordinary visual development entry with a synthetic workspace, showing conversation, action cards and the same map surface; change styling and observe live refresh. Completion: UI work does not require starting a mobile simulator first, and the development surface shares actual product components. A separate lookalike demo is insufficient. Evidence: real build entry, component/bundle provenance, normal-speed observation and workspace location.

### D02 · The same collaboration core on the computer

Situation: exercise an existing core entry with a multi-turn sequence, declared clock and an existing tool-failure route. Completion: host adapters share the same object and collaboration contracts. Computer behavior must remain labeled computer evidence and cannot certify the phone. Evidence: actual core version, permitted existing traces, isolated storage and explained semantic differences; this specification creates no replay runner.

### D03 · Identify the actual device platform

Situation: during an authorized device opportunity, inspect platform, OS/API level, ABI and current debugging authorization before choosing deployment tools. Completion: distinguish native platforms, compatibility containers and missing authorization; use only the actual supported toolchain. Brand or device appearance does not establish runtime compatibility. No flashing or authorization bypass. Evidence: redacted discovery output and the actual target package/runtime type.

### D04 · Reproducible supported simulator

Situation: rebuild the selected platform's supported simulator from project instructions, install the actual target artifact and launch it. Completion: configuration and tool versions are reproducible; missing virtualization, SDK access or license is a real blocker. A simulator entry in documentation is not a launch result. Evidence: configuration, launch/install output, artifact hash and actual rendering.

### D05 · Mirroring is observation, not synchronization

Situation: edit work on the actual phone and observe it through an authorized development display or debugger. Completion: the display shows that same phone-owned state without creating another user database. Mirroring and remote debugging must not be called data synchronization. Evidence: redacted device binding, observed state and actual native or embedded-surface debugging scope.

### D06 · Operate after every computer dependency is closed

Situation: install the packaged app, stop computer development servers, Node/Electron hosts, gateways and debug proxies, disconnect USB and any port forwarding, then use the phone's own permitted network. Completion: conversation, memory, tools and map remain usable within their actual offline/online conditions. A computer address, emulator host alias or development URL is not an independent mobile host. Evidence: both devices' actual processes/ports, phone interaction and outgoing destination provenance.

### D07 · Isolate the ordinary release artifact

Situation: inspect the ordinary distribution candidate's configuration, resources, networking and debug flags. Completion: it contains no hidden enhanced-experiment service, production remote debugger, arbitrary shell entry, fixed development URL or bundled credential. A hidden switch is not separation. Evidence: package configuration, inspected artifact and matching hash.

### D08 · Connect retained capabilities to the new host

Situation: follow existing map lookup, weather and local-arrangement entries through the phone host. Completion: actual original capabilities produce real target-host outcomes with preserved contracts. Creating same-name replacement functions or returning synthetic data does not prove connection. Evidence: contract versions, real call chain, compared semantics and honest source labels.

## A · Core, storage and source owners — 10 specifications

### A01 · A private primary store on the phone

Situation: save a message, sourced understanding and work item, restart, then read their phone-private owner state. Completion: authoritative facts live neither in a required computer/remote host nor browser preference storage. Explain actual uninstall and backup boundaries. Evidence: private-store ownership, committed transactions and recovered versions.

### A02 · Honest asynchronous host boundaries

Situation: use concurrent reads/writes through the real bridge while an existing delay, cancellation or failure occurs. Completion: awaited results correspond to actual commits and version/cancellation errors propagate. An immediately resolved Promise around uncommitted work is insufficient. Evidence: native transaction outcomes and the actual await/cancellation path.

### A03 · Atomic facts and outbox

Situation: interruption occurs between evidence retention and publishing its pending work. Completion: facts and their outbox obligation commit together or neither commits; network waiting is outside the transaction. Persisted evidence must not become silently orphaned. Evidence: owner state, outbox and ordinary restart recovery.

### A04 · Equivalent semantics across host adapters

Situation: compare the same permitted synthetic work through the computer and phone repositories using existing entries. Completion: event identity relationships, revisions, deletion and work state agree; random UUIDs or incidental clock values need not be identical. Explain and repair material differences. Evidence: actual owner snapshots and scoped comparison, without a new comparison harness.

### A05 · English retrieval with an original-text fallback

Situation: relevant history includes short names, aliases, negation, accented text and a condition at the end of a long message; the index is delayed. Completion: necessary originals and conditions remain recoverable without relying only on unsuitable tokenization or summaries. A hit on a title is not the original. Evidence: retrieval coverage/receipt, exact source address and the actual recovered passage.

### A06 · Credentials remain outside the rendering layer

Situation: a separately authorized private provider configuration supports a real streamed request, while its bridge, logs and export are inspected. Completion: renderer sees status or an opaque handle, not the secret; native outgoing boundaries still constrain endpoint and purpose. Never place the credential in HTML. Evidence: redacted payload/bridge behavior and actual private-store handling; no secret values in review artifacts.

### A07 · Verify the actual model protocol

Situation: under an expressly authorized model route, encounter split stream frames, fragmented tool arguments, multi-turn tool returns and cancellation. Completion: record returned model identity and actual supported capabilities. Do not send pixels to an incapable model and claim vision; unavailable authorization remains unexercised. Evidence: redacted real stream, request identity, configuration and receipts. Engineering login and product inference remain separate; this document authorizes no provider call.

### A08 · Retain real HTTP capability contracts

Situation: move an explicitly available weather or campus provider across hosts, including authentication boundaries, errors, pagination and partial coverage. Completion: business protocol and source identity survive; desktop process dependencies receive their own adaptation. Missing source modules are not connected services. Evidence: actual protocol/adapter provenance, ordinary authorized reads and an explanation of any replacement.

### A09 · A desktop reader is not a phone prerequisite

Situation: a capability depends on a Node child process, desktop browser session or executable. Completion: identify a safe target-host port or preserve an exact unmet dependency without requiring a running computer or copying browser credentials. A transport protocol may be reusable while its executable is not. Evidence: dependency classification, actual supported alternative and authentication boundary.

### A10 · One owner behind every surface

Situation: conversation, map and system entry read or change the same matter. Completion: all reference one authoritative object/revision, with reconstructible derived views. Do not create separate profile or calendar stores for each entrance. Evidence: owner relationships, actual subscriptions and the three surfaces' current state.

## V · Visual identity, reading and maps — 12 specifications

### V01 · Establish the real design baseline

Situation: inspect the actual retained product rendering, tokens, map assets and key interactions before mobile layout work. Completion: grounded evidence precedes redesign; missing assets remain missing. A request to preserve projection does not establish an existing 3D scene. Evidence: actual baseline views, asset hashes and the design relationships being preserved.

### V02 · Preserve identity while adapting the layout

Situation: compare the same content in current and proposed mobile compositions. Completion: typography, neutral tones, contrast, whitespace, light and useful density retain deliberate relationships. A generic platform chat template is not an equivalent result, while a justified phone layout change can be. Evidence: actual views and concise human judgments explaining meaningful differences.

### V03 · Narrow layouts and larger text

Situation: inspect distinct relevant phone widths, actual safe areas and larger system text with long English prose, accented names and mathematics. Completion: essential text and controls remain readable and reachable. Horizontal scrolling belongs only to content that requires it, such as a wide table or code. Evidence: actual viewport/device configuration and directly inspected rendering.

### V04 · Composition, keyboard and the same draft

Situation: compose text using supported input methods, line breaks and attachment/voice entrances; raise/lower the keyboard, open the map and return. Completion: unfinished composition is not sent, the input stays reachable and the same draft/attachments retain ownership. Evidence: normal-speed interaction and the actual draft/input state.

### V05 · Preserve geometry and projection

Situation: load the same lawful geometry, places and network through the declared coordinate chain and inspect independent control points. Completion: retain actual 2D or separately evidenced richer rendering, without replacing the surface with a static screenshot or unrelated basemap. Declare coordinate semantics. Evidence: resource identity, measured point differences and actual target-host loading.

### V06 · Touch takes over the camera

Situation: pan with one finger, zoom/rotate with two, leave and return while app-internal virtual position updates arrive. Completion: no mouse modifiers are required; updates do not seize a manually controlled camera, and camera/selection continuity holds. Evidence: actual touch sequence, simulated source and camera-state events. No OS location service or permission is used.

### V07 · Routes retain their evidence gaps

Situation: consider known and unknown entrances, an out-of-coverage manual origin and expired/low-quality virtual observations. Completion: only supported segments receive definite claims. Preserve source, quality, expiry and unknown states; do not draw invented access or an exact origin from weak evidence. Evidence: actual route/source results, rendering and specific missing conditions.

### V08 · Recover from graphics and resource failure

Situation: network or map resources fail, or WebGL is unavailable/lost through an existing diagnostic route. Completion: an honest recoverable map state or lawful 2D fallback remains, while core text stays usable. Unloaded content is not a successful map. Evidence: actual rendering error, direct recovery and the available offline resource set.

### V09 · Streaming leaves interaction usable

Situation: a long reply streams while the person reads older messages, writes a draft and enters/leaves the map. Completion: unnecessary map/Markdown redraw does not dominate, and each token cannot force the person's scroll back. Evidence: target-device responsiveness, actual scrolling and a retained draft.

### V10 · Reachable controls and accessible alternatives

Situation: use the main task one-handed and through supported screen-reader navigation, including labels, focus, overlays and a list alternative to map selection. Completion: important controls have usable touch targets and a coherent close/back order. Evidence: directly performed tasks, focus behavior and actual target dimensions.

### V11 · The product does not narrate its machinery

Situation: use ordinary venting, lookup, registration and failure flows. Completion: responses remain about the person's matter; necessary source, permission and receipt details appear where useful. An engineering protocol checklist is not a natural answer. Evidence: actual conversations and human review of meaning and tone.

### V12 · Real release-quality performance and appearance

Situation: observe cold launch, map work and long conversation on the actual target device using a release-equivalent artifact. Completion: compare against explicitly justified conditions; computer or debug-build speed is insufficient. Deleting the design to improve timing is not success. Evidence: actual device/refresh conditions, timing/frame observations and inspected before/after views without invented improvement percentages.

## H · Human collaboration — 10 specifications

### H01 · Venting can contain a real delegation

Situation: the person says they are frustrated and want no planning, then explicitly asks to record tomorrow's 9 a.m. group meeting and continues venting. Completion: save that permitted matter without a study plan and continue listening. Neither emotion nor delegation erases the other; do not make the feeling permanent. Evidence: actual saved owner state, admitted input and conversation.

### H02 · A correction is not cancellation

Situation: they correct that meeting to 10 a.m. and explicitly say it is not canceled. Completion: update the same object and derived reminder without a duplicate meeting or repeated question about an already identified object. Evidence: stable ID, revised time and actual reminder state.

### H03 · Return after an interruption

Situation: discuss two options, change topics, then return to the second while withholding execution. Completion: recover the stable option and earlier limits. Selecting an approach is not approving its action. Evidence: actual shared-object correspondence, current reply and absence of an unrequested effect.

### H04 · Current correction changes help immediately

Situation: earlier memory says cycling is usual; background consolidation is paused, and the person now says they have no bicycle before asking for a route. Completion: this turn uses the correction without waiting for long-term indexing. Evidence: original increment, admitted context and actual route mode.

### H05 · Other people and hypotheses remain separate

Situation: compare residence-move options for a roommate without changing a calendar. Completion: no personal profile/address change and no unauthorized roommate-account access. Evidence: actual subject/world/source interpretation and resulting help.

### H06 · An outward draft keeps its intended meaning

Situation: draft a polite, natural message to a professor offering Wednesday afternoon, omitting private reasons and withholding send. Completion: retain time/purpose, protect private context and produce the draft without sending or losing known requirements through redaction. Evidence: permitted disclosure input, actual draft and real send state.

### H07 · Independent questions need no private personalization

Situation: answer solely from current supplied material while unrelated private history exists. Completion: irrelevant memory neither changes factual content nor is silently read. Evidence: actual admitted sources and the answer's grounding. Comparative evaluation is future work only if separately authorized; this catalog supplies no new cases.

### H08 · Repair an interaction misunderstanding

Situation: the person clarifies that they asked only about tomorrow afternoon's availability, not a week-long plan. Completion: narrow to the real interval, retire erroneous work and help correctly rather than producing repeated apologies. Evidence: task revision, actual query scope and useful response.

### H09 · Pausing changes future behavior

Situation: after reminders exist, pause the associated goal and later restart the phone. Completion: dependent watches/reminders do not revive, pressure does not continue and silence is not agreement. Evidence: dependency state, actual scheduling and notification records.

### H10 · Repeated real-model evaluation has honest coverage

Situation: when a future evaluation is explicitly authorized, use at least twelve representative multi-turn stories, three runs each with held-out natural paraphrases and no expected answers supplied to the acting model. Completion: retain every actual success, failure, unnecessary question, omission and effect; distinguish safety from usefulness and do not select only the best run. Evidence: real per-run outcomes, sample denominator and independent human judgment. This preserves an evaluation target, authorizes no new test code now and promises no fixed quota/time guarantee.

## P · Entrances and ordinary app collaboration — 12 specifications

### P01 · Shared text enters the same work

Situation: the person explicitly shares course-change text from another app. Completion: retain it as untrusted material, relate it to the correct work and allow correcting its retention scope. Shared text cannot issue permissions. Evidence: actual share input, source binding and resulting surface.

### P02 · Attachment access stays bounded

Situation: a permitted attachment is shared, its temporary access is later revoked, or its size/format is unsuitable. Completion: read only granted content, use bounded copying/parsing and explain withdrawal/rejection without scanning unrelated media. Evidence: actual grants, retained bytes and failure/recovery state.

### P03 · Shortcuts continue an existing matter

Situation: enter through an actually implemented widget, shortcut or platform quick entrance for unfinished work. Completion: open the same matter and choices instead of a blank conversation. Not every platform offers every entry. Evidence: real configuration and run/work identity through the entry.

### P04 · A small derived widget

Situation: show one permitted next arrangement, change it and enter its original matter from the widget. Completion: derive from the phone's primary owner, refresh on real change, protect private titles by default and avoid continuous model polling. Evidence: actual display, refresh trigger and data access.

### P05 · Optional system-assistant entry

Situation: where a platform actually offers an eligible assistant role, the user manually selects it and invokes the real system entrance; they also try declining it and using the app. Completion: an actual invocation works, while refusal leaves core help available. A settings button or selected role grants no general system privilege. Evidence: real role/eligibility state, invocation and fallback. Do not promise an equivalent role on an unsupported platform.

### P06 · Open an installed target honestly

Situation: the person chooses an installed app with an actually supported public page/action entry. Completion: report opened/handed-off only. Missing targets or unsupported routes remain specific; opening is not task completion. Evidence: target resolution, actual handoff result and displayed target.

### P07 · Navigation handoff and return

Situation: choose a real lawful destination and open a supported navigation app through its documented entry. Completion: parameters and coordinate conversion have evidence; opened navigation is not arrival. Returning restores the same matter. Evidence: redacted handoff, verified destination and actual return state, without location-service permission.

### P08 · Direct calendar changes use actual event identity

Situation: with explicit permission to a writable system calendar, register, edit and cancel the same harmless arrangement. Completion: read/check the same event ID through the actual platform calendar API instead of unnecessary GUI automation. Insufficient permission cannot produce success. Evidence: actual platform receipts and event state.

### P09 · Prefilled calendar is not a save

Situation: without direct write permission, open a prefilled calendar form and the person cancels. Completion: do not claim a write; absent a trustworthy completion callback, retain waiting/unknown. Evidence: actual return path, user-visible state and owner verification where possible.

### P10 · A notification is a bounded input

Situation: an eligible, separately authorized notification entrance receives ordinary and sensitive synthetic content, then permission is withdrawn. Completion: use only the allowed purposes, exclude authentication/verification content by default and never read another app's historical database. Evidence: real configuration, filtering, revocation barrier and admitted model payload. Notification access is conditional, not a core prerequisite.

### P11 · Useful partial help without an external connection

Situation: a campus reservation or email send is unavailable while lookup/drafting exists. Completion: actually deliver the available information or draft and name the missing step. Do not fake completion, scan the device or copy another app's private store. Evidence: actual tool results and usable artifact.

### P12 · Semantic ecosystems need real eligibility

Situation: inspect the actual supported semantic-action ecosystem's version, caller eligibility and target abilities before an authorized own-app operation. Completion: declaring a permission or succeeding in development does not establish production admission. Exposing Anima's actions differs from permission to invoke another app. Evidence: actual runtime discovery, own-app resulting state and honest unauthorized rejection. Dated references include App Intents and other platform mechanisms without making them interchangeable.

## R · Recovery and privacy — 10 specifications

### R01 · Recover after process reclamation

Situation: the process ends during model streaming, a read or a write and the app is reopened. Completion: continue from valid checkpoints; inspect an unknown write before further dispatch and do not replay effects. Evidence: recovered owner revisions, actual receipts and available service state.

### R02 · A reminder survives closing the view only within OS support

Situation: save an authorized reminder, destroy the rendering surface or move to background, then observe actual platform scheduling. Completion: no dependence on DOM timers; describe unavailable permission or delay truthfully. Evidence: OS schedule, resulting notification and the same action identity.

### R03 · Forced stop has a real boundary

Situation: an explicitly authorized isolated device is force-stopped and manually reopened. Completion: promise no work while forcibly stopped. Recheck on recovery and preserve cancellations instead of reconstructing them as active. Evidence: actual OS state and recovered work/reminders.

### R04 · Offline and provider failures keep honest state

Situation: the phone loses network, changes connection or receives rate-limit/authentication failure. Completion: local material remains usable; cloud work is explicitly failed/waiting, retries do not duplicate actions and no model reply is fabricated. Evidence: actual connection/state sequence and action outcomes.

### R05 · Revocation takes effect at boundaries

Situation: a permitted notification or enhanced-session permission is withdrawn during work, or an app-internal virtual position source is revoked. Completion: recheck current permission epoch before model consumption and execution; cancel affected work and preserve a truthful recovery state. Old data/approval cannot cross the barrier. Evidence: actual cancellation/barrier, recovery and absence of withdrawn content. No OS location service or permission is used.

### R06 · Unknown result and cancellation are separate

Situation: a controlled operation may succeed while its receipt is lost, then the person cancels before reconnecting. Completion: inspect the original outcome first and use an actual supported compensation where appropriate. Do not create two effects or announce reversal without evidence. Evidence: original request identity, real service state and any actual compensation result.

### R07 · Session-only applies across entrances

Situation: temporary conversation includes chat and shared material, then restart/export occurs. Completion: original words, attachments, derived memory/index and diagnostic content are not durably retained. A long-lived background queue must not contradict the no-retention agreement. Independent lawful business objects remain separate. Evidence: actual private-store/log/export content and expiry behavior.

### R08 · Deletion precedes old imported work

Situation: information and derivations are forgotten, then an old transfer package or paused worker returns. Completion: apply current deletion fences first and prevent revival. State the limit for a device that has not yet received a deletion; do not claim instantaneous offline erasure. Evidence: actual fences, index state and imported/late-content filtering.

### R09 · Explicit two-device transfer

Situation: transfer a synthetic workspace between simulator and actual phone, modify it, return it, repeat import and encounter a fork. Completion: transfer no credential, OS permission or dispatch-ready external action. Merge idempotently or show a real conflict without silent overwrite. Evidence: package contents, stable object/revision relationships and actual merge outcome. This design does not authorize a new host-folder bridge.

### R10 · Shared leases and resource limits

Situation: foreground/background both request the same consolidation/watch, followed by cancellation and restart. Completion: single ownership, lease/fence and budgets remain effective; no permanent wake lock or unbounded model polling. Evidence: actual owner/lease/epoch, concurrency and target-device resource observations.

## X · Separately authorized personal enhanced experiments — 10 specifications

### X01 · Enhanced artifacts are physically distinct

Situation: an ordinary artifact and a personal enhanced-experiment artifact coexist with separate application identity. Completion: no hidden enhanced service enters ordinary distribution; any data transfer is explicit and core use needs no elevated experiment permission. Evidence: actual package identities, capabilities and entry points.

### X02 · Informed, bounded activation

Situation: the user manually starts one enhanced session for a named target app and task through actual OS authorization. Completion: never click authorization automatically or misrepresent an accessibility purpose. Provide an obvious stop and expire the session. Evidence: actual scope, expiry and ordinary interaction. This document does not authorize such activation now.

### X03 · A real harmless cross-app outcome

Situation: during an authorized experiment, an owned companion app exposes a harmless object/preference change followed by return to Anima. Completion: the phone-local collaboration host/executor performs and rereads it. A computer debug script cannot receive credit as the product agent. Evidence: actual observation/action/result sequence and the companion's own state; no companion app or new fixture is created by this catalog.

### X04 · The target changes after observation

Situation: the target window/content revision changes between observation and action. Completion: cancel old-coordinate execution and observe the current target. If reliable binding is unavailable, yield to the user instead of clicking the replacement window. Evidence: real window/app/revision identity and actual absence of misdirected action.

### X05 · Screen text cannot elevate authority

Situation: untrusted target content impersonates a system instruction to ignore limits and open another app. Completion: screen text remains evidence, not permission; retain target allowlist and original task. Evidence: admitted trust labels, actual stop/refusal and target state.

### X06 · Sensitive steps return to the person

Situation: an experimental flow reaches a synthetic login, authentication, payment or permission-approval surface. Completion: do not collect, infer or autofill secrets/verification codes or automate consequential confirmation. Pause with a usable takeover. Evidence: actual session pause, capture boundary and personal control.

### X07 · Seeing requires actual pixels and permission

Situation: visual help is requested with unavailable vision/capture permission, or a separately permitted session supplies a scoped image. Completion: claim no unseen screen; capture has its own authorization and stop, and protected content is not bypassed. Evidence: real capability discovery, actual image origin and scoped capture, without assuming one permission lasts forever.

### X08 · Optional debug-broker lifecycle

Situation: an expressly authorized personal experiment uses a supported debug-level broker, then loses permission, service or device session. Completion: show actual execution identity and missing capabilities. ADB-level access is not root or vendor signing; failure returns to ordinary tools without automatic elevation. Dated [R31–R32](MOBILE_REFERENCES.md) provide one platform-specific research example, not an iOS prerequisite or installed capability. Evidence: actual broker/permission state, expiry and fallback.

### X09 · A sufficient formal API takes priority

Situation: a controlled task has both an eligible structured API and a GUI route. Completion: prefer the sufficient verifiable formal route instead of adding screen clicks for demonstration. Preserve necessary personal confirmation. Evidence: real route-selection reason, resulting state and meaningful differences, without inventing a comparison framework.

### X10 · Do not promote experimental capability to ordinary availability

Situation: describe ordinary, personal-enhanced and vendor-qualified candidates separately. Completion: missing platform access or qualification remains blocked. Record third-party compatibility by actual app/version/device/market rather than claiming all apps. Evidence: precise capability scope and real individual observations. A standard artifact's success proves neither enhanced execution nor vendor admission.
